# STRESS — Sandbox demo-run abuse/cost proof (CAISSON-110)

- **Exit criterion 3** of `PLAN.md` (ADR-0350 F5 / ADR-0352): a scripted burst ≥ 3× the daily
  cap proving 429 rate-limits, an atomic exactly-cap admission, 503 daily-cap after trip, the
  kill-switch 503, and that the excerpts stay lit when the run path is dark.
- **Harness:** `apps/site/scripts/demo-run-stress.ts` — a LOCAL route-level harness (never CI,
  never production). It drives the REAL `handleDemoRun` against a REAL Postgres (PGlite via
  `@caisson/testing`, the same lane the store + account-store integration tests use), with the
  REAL rate-limit account-store, the REAL F5 budget reserve/release, and the REAL lead telemetry.
  Only two orthogonal seams are faked, both covered elsewhere: Turnstile (fail-closed 403 proven
  in `lib/demo-run/handler.test.ts`) is forced-pass so every request reaches the quota gates, and
  the in-process generator (proven in `lib/demo-run/run.test.ts`) returns a fixed tiny artifact so
  the proof isolates admission control.
- **Run:** `bun apps/site/scripts/demo-run-stress.ts` → exit 0 on all invariants held.

## What each leg proves

| Leg                          | Setup                                                                                      | Result                                                                                     | Invariant                                                                                                                                                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Rate limit**            | 1 IP, per-IP capacity 5, 1h window, F5 caps high                                           | attempted 20 → **5×200, 15×429**                                                           | The per-IP token bucket drains at exactly capacity; every 429 carries a `Retry-After`.                                                                                                                                                 |
| **B. F5 daily cap (atomic)** | 35 distinct IPs fired **concurrently**, dailyCap 10, concurrency cap high, rate limit high | attempted 35 (3.5× cap) → **10×200, 25×503 daily-cap**; `runs_started=10`, `concurrency=0` | The guarded `UPDATE … WHERE runs_started < cap RETURNING` admits EXACTLY the cap — never over-admitted (`runs_started` lands on 10, not 11) even under a concurrent last-slot burst; every admitted run released its concurrency slot. |
| **C. Kill switch**           | `DEMO_RUN_ENABLED=false`, one request                                                      | **503 `disabled`**, no budget row written                                                  | The kill switch fails closed BEFORE any reserve/generate — zero cost when dark.                                                                                                                                                        |
| **D. Flag independence**     | `DEMO_RUN_ENABLED=false`, excerpts key unset                                               | run path **disabled**, excerpts **lit**                                                    | The run-path kill switch (`DEMO_RUN_ENABLED`) and the excerpts flag (`NEXT_PUBLIC_DEMO_EXCERPTS_ENABLED`) are two independent env keys (ADR-0352 F2) — darkening one never darkens the other.                                          |

## Notes / caveats

- PGlite is a single in-process connection that serializes transactions, so leg B proves the
  WHERE-guarded conditional-`UPDATE` **correctness** (no over-admission even when many admissions
  observe the same last slot), not OS-level multi-backend contention. This is the same caveat and
  the same accepted proof shape as `packages/rate-limit`'s account-store race test and
  `lib/demo-run/store.test.ts`'s concurrent-last-slot test; the cross-backend exactly-one guarantee
  rests on Postgres READ COMMITTED re-evaluating the inlined guard.
- Email is telemetry only throughout — never a quota key (the leads write is best-effort and never
  gates admission).

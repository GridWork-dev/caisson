# T2 · Risk & Security Assessor

1. **Launch-blocking — WORM claim mismatch:** the homepage presents S3 Object Lock in COMPLIANCE mode as the shipped posture and promises resistance even to a leaked root key, while `S3ArtifactStore` defaults to GOVERNANCE and the sole live proof explicitly never tests COMPLIANCE, so probability is certain, impact is high trust/compliance-claim liability, and the cheapest mitigation is to label GOVERNANCE as the proven default and COMPLIANCE as an unproven explicit opt-in until a live irreversible proof exists (**CORROBORATED** — E-B2, E-B3; `apps/site/app/(marketing)/page.tsx:64`, `packages/audit-worm/live/store.s3.live.test.ts:11`).
2. **Launch-blocking — license root-of-trust concentration:** the private Ed25519 license key is loaded from an environment variable into the same approximately 23k-LOC public HTTP service that accepts webhooks and issues licenses, while the KMS signer is explicitly unwired, creating a low-to-medium-probability but high-impact path from any service RCE or dependency compromise to arbitrary perpetual offline licenses that local verification cannot revoke; the cheapest durable mitigation is to move signing behind a narrowly authorized KMS/HSM signer before paid checkout opens (**CORROBORATED** — E-A4, E-A9; `packages/license-issue/src/signer.ts:23`, `services/license/src/server.ts:82`).
3. **Launch-blocking proof gap — tenant isolation:** the RLS code substantively closes the known owner, BYPASSRLS, missing-filter, and empty-GUC paths, but the cited proof is PGlite/CI rather than the deployed Neon/pooler schema, leaving a low-probability, catastrophic-impact migration-or-role-drift path whose cheapest mitigation is one launch-vault receipt combining production `pg_class`/`pg_roles` attestation with missing-filter, cross-tenant, and reset-to-empty pooled-connection probes (**CORROBORATED** — E-B2, E-B3, E-B6; `packages/tenancy-rls/src/rls.ts:35`, `packages/tenancy-rls/src/rls.integration.test.ts:50`).
4. **Launch-blocking availability risk — non-atomic audit append:** `AuditChainStore.append` performs the external write-once WORM put inside the database transaction, so an after-put/before-commit failure can occupy that chain length while rolling back the row and then stall every retry, a low-to-medium-probability, high-impact loss of evidentiary availability whose cheapest mitigation is a deterministic fault-injection proof plus a documented recovery path that preserves the original immutable anchor (**CORROBORATED** — E-B2, E-B3; `packages/audit-worm/src/chain-store.ts:21`, `packages/audit-worm/src/chain-store.ts:337`).
5. **Post-launch contractual risk — “perpetual-per-major” is not enforced by verification:** `major` is signed and described as the version boundary, but `verifyLicense` accepts no expected major and the live registry resolver ignores `claims.major`, so an authentic older-major token remains cryptographically valid at later-major call sites, a high-probability-at-first-major, medium-impact licensing leak whose cheapest mitigation is an `expectedMajor` check in the verifier contract and every entitlement gate before the first major bump (**CORROBORATED** — E-A9; `packages/license-verify/src/claims.ts:30`, `packages/license-verify/src/verify.ts:83`, `registry/worker/entitlement-filter.ts:39`).

**Recommendation:** Hold the paid launch gate until findings 1–4 have receipts: correct the homepage under ADR-0080 without changing ADR-0040’s compliance hero, prove the real COMPLIANCE option before advertising its root-resistant property, attest RLS against the deployed pooler path, demonstrate safe recovery from the WORM/DB split-brain fault, and remove raw signing-key custody from the public issuer process; queue finding 5 as a required precondition for the first major-version release, because it does not expose customer data or weaken current-major verification today.

**Confidence:** high.

**What would change my mind:** a single pinned launch-vault security receipt showing a live COMPLIANCE-mode retention/delete-denial proof, deployed Neon/pooler RLS isolation proof, successful recovery from an injected after-WORM-put/before-DB-commit failure, and KMS/HSM-backed license signing would change my recommendation from hold to proceed.

## Notes (informational, not findings)

- **Trust-class parity with `discord-notify.ts`.** The new file is a structural twin of the ADR-0203 Discord push — same `loadXxxConfig` shape, same `null`-on-unset, same never-throw contract, same `void ... .catch(() => stderr)` injection, same plain `fetchWithTimeout` (no `ssrfGuard` wrapper). The PostHog ingestion host (`https://us.i.posthog.com` default) and `SUPPORT_BOT_URL` are both operator-env-controlled, so neither requires the buyer-URL SSRF kernel guard added under ADR-0204. If a future hardening pass wires `ssrfGuard` into `discord-notify.ts`, it should land on `posthog-capture.ts` in the same change for consistency — but the current absence is not a vulnerability.
- **Async-rejection test coverage.** Test #2 covers only the synchronous-throw arm. The async-rejection arm relies on the `.catch(() => stderr)` at `app.ts:379-383` (the ADR-0203 template, proven in production). Not a blocker.
- **No new attack surface introduced.** No new endpoint, no new auth surface, no new buyer-controlled input read. The diff adds one outbound POST to an operator-configured host with an operator-configured API key, gated on a verified grant. The buyer's `accountId` already flows into the dashboard PostHog `identify()` (per ADR-0237 F8 spec) and into the ADR-0203 Discord push — no new data leaves the trust boundary.

# W1 Research 2/4 — Credits Ledger: Grant-Level Expiry + FIFO Burn (ADR-0245)

## 1. Current schema + grant/debit algorithm (file:line)

**Schema** — `packages/credits/src/schema.ts:8-51` (`CREDIT_SCHEMA_SQL`, shipped live as `0002_credits.sql`, `apps/site/lib/deploy-migrate.ts:73`):

- `credit_wallet(account_id PK, balance integer)` — **one row per account, one aggregate integer.** No per-grant remaining balance anywhere.
- `credit_event(id, account_id, event_type, amount, feature, source_event_id, idempotency_key, created_at)` — append-only, signed `amount` (+grant / −debit). Two partial-unique idempotency indexes (ADR-0024) + a one-of-two `CHECK`. Two additive migrations already layered on top without editing the frozen `0002` string (the load-bearing precedent for how expiry must land): `CREDIT_ROUNDING_MIGRATION_SQL` (`schema.ts:66-77`, shipped `0007_credit_rounding.sql`) and `CREDIT_LINE_ITEM_MIGRATION_SQL` (`schema.ts:99-107`, shipped `0009_credit_line_item.sql`).
- Live migration ledger (`deploy-migrate.ts:67-125`) is at **`0013`** in-repo; Railway prod is applied through `0006`-`0013` per `docs/deploy/STATE.md:129-131`. Numbered migrations are checksum-pinned and forward-only (ADR-0006 discipline cited at `schema.ts:63,95`; `deploy-migrate.ts:86-88,90-93`) — **any expiry delta ships as a new `00NN_*.sql` append, never an edit to `0002`.**

**Grant** (`credits.ts:217-244`): `assertPositiveInt` → idempotency-column resolve → `INSERT credit_event` (`ON CONFLICT DO NOTHING RETURNING id`, absorbs a replay) → `UPSERT credit_wallet … balance = balance + $2`. No concept of "this grant's remaining balance" — the moment it lands, its value is folded into the single aggregate `balance` and its individual identity is gone except as a ledger row.

**Debit** (`credits.ts:251-284`): insert the negative ledger row → `UPDATE credit_wallet SET balance = balance - $2 WHERE balance >= $2` (atomic floor, debit-before-spend, ADR-0049 `codegen_debit` fires at generation entry inside `withTenant`, ADR-0093 scopes it to the hosted path only, local CLI is free). **The debit draws against the pooled `balance` — it has no notion of _which_ grant(s) it is consuming.** This is the crux of the FIFO gap: today there is no data path that could answer "was this debit paid for by the grant expiring in 3 days or the one issued yesterday?"

`clawback` (`credits.ts:466-518`) is the closest existing precedent for "reverse part of a specific grant" — it locks the wallet row (`FOR UPDATE`), computes `min(amount, currentBalance)`, and writes one compensating `refund_clawback` row. Per-line provenance (`lineCreditLedger`, `credits.ts:404-428`) already demonstrates the pattern of deriving a sub-balance for one grant (`granted − clawed`) via `SUM(amount) FILTER (...)` over `credit_event` filtered by `line_item_id` — this is architecturally the nearest cousin to what a per-grant remaining balance needs, just scoped to refunds instead of expiry.

## 2. Schema delta + 3 implementation shapes

**Common delta regardless of shape:** add nullable `expires_at timestamptz` to `credit_event`, populated only on grant rows (`GRANT_EVENT_TYPES` — `credits.ts:19-24`), ships as `0014_credit_expiry.sql` mirroring the `CREDIT_ROUNDING_MIGRATION_SQL` append pattern (`schema.ts:66-77`). Set at grant time in `grant()` (`credits.ts:217`), typically `created_at + interval '12 months'` computed application-side and passed in (keeps the 12-month constant out of SQL, easy to override per class per the ADR's "unless a later ADR states otherwise" clause).

| Shape                                              | What it adds                                                                                                                                                                                                                                                  | Remaining-balance query                                                                                                    | Debit-time cost                                                                                                   | Append-only?                                                                                                                                                                                   |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Mutable `remaining` column on the grant row** | `remaining integer` on `credit_event`, decremented by every debit that draws from it                                                                                                                                                                          | O(1) index read                                                                                                            | Debit must `UPDATE credit_event SET remaining = remaining - x WHERE id = grant_id`                                | **Violates append-only** — the ledger row is mutated post-insert, breaking the "ledger is the billing source of truth, audit trail never changes" invariant ADR-0007 relies on (`ADR-0007:22`) |
| **B. Derived-from-ledger**                         | Only `expires_at`; no new table. FIFO remaining computed at read time via a running-sum window query per account (cumulative grant amount vs. cumulative debit amount, ordered by `created_at`)                                                               | O(n) over the account's full event history every time (expiry sweep, dashboard badge, or an eventual per-grant audit need) | **Zero** — debit stays exactly as it is today, no new write                                                       | Fully append-only                                                                                                                                                                              |
| **C. `grant_consumption` join table**              | New append-only table `grant_consumption(id, grant_event_id, debit_event_id, amount, created_at)`; `debit()` walks unexpired grants oldest-first and writes 1..k rows per debit (splits across grants when one grant's remainder can't cover the whole debit) | O(1) indexed `SUM(amount) WHERE grant_event_id = $1`                                                                       | Debit becomes a loop: read remaining-per-grant (indexed), insert N consumption rows, occasionally spans 2+ grants | Fully append-only, and the _most_ auditable (literal trace of which debit ate which grant)                                                                                                     |

**Recommendation: C, medium confidence.** B is genuinely simpler (one nullable column, zero debit-path changes) and honors "expiry is additive" most literally, but the derived-from-ledger scan is exactly the query an **expiry sweep job must run for every account, on every sweep cycle** — at any real subscriber volume this becomes the expensive path B was trying to avoid touching, and it recomputes the same FIFO waterfall from scratch each time instead of ever writing it down once. A is disqualified outright: it mutates a ledger row, which is a direct hit on the append-only invariant the whole credits package is built to protect (ADR-0007, ADR-0006 precedent). C costs more code (debit path now loops and may write multiple rows) but is the only shape where "how much of grant G is left" is both cheap to query _and_ never assumed — it's derived once, at consumption time, from real writes. Given credits are literally money, paying the extra debit-path complexity for an auditable, indexed-cheap answer is the right trade. **If launch-scale debit volume is trivial enough that a B-style full-ledger scan per sweep is provably cheap (worth measuring before building C), B is the legitimate cheaper fallback** — flag this as a build-time call, not a re-litigation of the policy ADR.

## 3. FIFO tie-break fork — concrete cases + rules

**Can ties on `created_at` actually happen?** Yes, and there's a real, already-shipped example: Postgres `now()` (the DEFAULT for `created_at`, `schema.ts:26`) returns the **transaction start timestamp**, constant for the whole transaction — not per-statement. ADR-0218's multi-item Paddle cart writes **N per-line `purchase` grant rows in one webhook-handling transaction** (`schema.ts:80-92`, `credits.ts` `lineItemId`/`lineChargedAmount` plumbing) — every line of that cart grants with **byte-identical `created_at`**. That's the concrete tie case, not a hypothetical race. A second, rarer case: a promo/bonus grant issued in the same transaction as a `sub_allotment` renewal.

Tie-break options:

1. **`id` (random UUID) as secondary sort** — already the precedent (`getLedger` orders `created_at, id`, `credits.ts:313`). Free, stable, but semantically arbitrary — doesn't correlate with anything about the grant.
2. **`expires_at ASC` then `id`** — free once `expires_at` is stored (shape above), matches the _stated intent_ of FIFO ("balances near expiry burn first"): when two grants tie on issue time but carry different expiry (e.g. one class gets a shorter override expiry per the ADR's carve-out), this genuinely burns the sooner-expiring one first. For the common real tie (multi-line cart, same class, same expiry) it degenerates to a no-op and needs a further tie-break anyway.
3. **New monotonic sequence column** (`BIGSERIAL`/`ctid`-derived) as the tie-break — deterministic physical-insert order even within one transaction (so the per-line loop order in the multi-item cart is preserved exactly). Costs a new column + index; only matters when case 2 also ties (same class, same expiry, same transaction) — which is precisely the ADR-0218 real-world case.

**Recommendation: 2 then 3 (expires_at ASC, id/sequence as final tie-break), medium-high confidence.** Rule 2 is free and is the only option that's actually _meaningful_ against the policy's stated goal; it should be the primary tie-break. Because the one real tie case in the codebase today (multi-line cart) ties on expiry too, a final deterministic tie-break (rule 1's `id`, no need to build rule 3's new column) is sufficient — building a dedicated sequence column solves a tie that, in practice, never needs more than "pick one, deterministically" since same-cart-line grants are fungible by construction.

## 4. Expiry-notification posture

Infra reality check: `packages/email` ships exactly **3 templates today** — `magic-link`, `verify-email`, `password-reset` (`packages/email/src/templates/index.ts`, confirmed via `find`) — **zero transactional/billing templates exist** (no receipt, no invoice, no usage-alert email). The dashboard credits page (`apps/site/app/dashboard/credits/page.tsx:1-80`) already reads `getLedger`/`balance` and renders `MetricStat`/`LedgerList` — it has no expiry-aware read today but the read+render path is already wired. `@caisson/jobs` (harvested, ADR-0211) now has an idempotent-enqueue + claim/SKIP-LOCKED consumer API — the natural home for a periodic sweep, but building one is genuinely new plumbing, not a reuse.

| Option                                                                          | Build cost                                                                                                                                                                                                                | Grounding                                                                                                                                |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **None**                                                                        | Zero                                                                                                                                                                                                                      | Matches ADR-0245's own posture — the ADR names the ledger delta as the only thing "scheduled for build," says nothing about notification |
| **Dashboard badge** (e.g., "120 credits expire in 14 days" on the credits page) | Low — one new read (whichever shape's remaining-per-grant query) + one UI element on an already-built page                                                                                                                | Reuses `dashboard-reads.ts` + the existing `MetricStat` component pattern (`credits/page.tsx:56-62`); no new package, no cron            |
| **T-30d email**                                                                 | High — needs a net-new email template (0→1 in the billing/transactional category), a scheduled sweep (new `@caisson/jobs` cron consumer), and a per-grant "already notified" idempotency marker to avoid re-sending daily | No existing precedent to build on; this is the first transactional-billing email the product would ever send                             |

**Recommendation: dashboard badge now, defer email, medium confidence.** Pre-launch posture (no Paddle PRODUCTION account yet — `docs/state/launch-runbook.md:78`) means there's no real subscriber base to email; building the first transactional-email template + a cron consumer for a notification that has zero recipients yet is speculative. The badge is nearly free given the page and read layer already exist, and covers the actual near-term risk (an operator or design-partner buyer discovering unexpectedly expired credits with no visibility). Revisit the email track once Paddle PRODUCTION exists and there's a real cohort to notify.

## 5. Live-data backfill exposure

**Yes — live grant rows exist in the prod Railway Postgres today**, but they are **Paddle SANDBOX-backed, not real customer money.** Evidence: `docs/state/launch-runbook.md:13-14,33-35,78` — the whole platform is explicitly pre-launch, Cloudflare-Access-gated, "Paddle is wired end-to-end today, but against the SANDBOX catalog," and Paddle PRODUCTION account creation is still an open pre-launch step (P1, `launch-runbook.md:78`). The launch-runbook's own live-verify checklist requires "a real purchase granted correctly in Prod" (`launch-runbook.md:358,479`) as a _precondition_ for going live — meaning the SANDBOX purchases already exercised end-to-end (§2 verify, the admin grant→revoke round-trip in `docs/deploy/STATE.md:134-135`, CAISSON-17) **did write real `credit_event`/`credit_wallet` rows to the live DB** to prove the pipeline.

**Consequence for the migration:** any `00NN_credit_expiry.sql` adding `expires_at` must decide a backfill value for these pre-existing NULL-expiry rows — options are (a) backfill `created_at + 12mo` retroactively (treats them as if issued with the policy from day one — cleanest, matches "additive" framing) or (b) leave pre-existing grants un-expiring (`expires_at IS NULL` = never expires) and only apply the 12-month clock to grants issued after the migration lands (simpler, avoids surprise-expiring a SANDBOX-proof grant, but creates a permanent two-tier ledger). **Recommend (a), high confidence** — there is no real money at stake in these rows (SANDBOX test data), so retroactively dating them costs nothing and avoids shipping a permanently-branched expiry model into a fresh ledger for its very first grants.

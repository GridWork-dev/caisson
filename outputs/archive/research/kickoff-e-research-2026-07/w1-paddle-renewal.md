# W1 Research 3/4 — Paddle Updates-Renewal SKU Plumbing (Sandbox)

## 0. Governing policy (already locked)

ADR-0244 (`knowledge/decisions/ADR-0244-perpetual-updates-window.md:1-37`) locks the **policy**: every one-time purchase is perpetual-use + 12mo of updates included; an optional renewal at ~40% (35-50% band) of then-current list buys +12mo more; subscriptions are unaffected. It explicitly says: _"The updates-renewal SKU family... is created at the checkout-flip session, not before"_ (line 36) and names the registry/entitlement window-check as _"named here, not built now"_ (line 32). **Nothing renewal-shaped exists in code yet** — confirmed by an empty grep for `updates_window|update_window|updatesWindow|updates_expires` across the repo. This research maps what the renewal wave must plug into.

## 1. Current catalog + fulfillment flow (file:line)

**Catalog / price-id books** — `packages/pricebook/src/`:

- `purchases.ts:51-254` — `PURCHASE_BOOK`: `providerPriceId -> {purchaseTag, credits, entitlements[]}`. One-time SKUs only (editions, bundle, 11 à-la-carte modules, 1 credit pack). Every real row is `credits: NO_CREDITS` (license-only) except the credit-pack row. Fail-closed `resolvePurchase()` (`purchases.ts:268-277`) — unknown price id throws.
- `plans.ts:63-94` — `PLAN_BOOK`: the parallel table for **subscriptions** (`resolvePlan()`, `plans.ts:102-113`). Not the renewal path (renewal is optional/one-time per ADR-0244 §4) but structurally the sibling to look at for the "N SKUs keyed by price id, versioned book" pattern.
- Dollar amounts live nowhere in these books — `apps/site/lib/pricing.ts` is the display SoT (`purchases.ts:69-72`); the Paddle product/price dashboard holds the charged amount. ADR-0227 (`knowledge/decisions/ADR-0227-compliance-reprice-and-module-catalog.md:36-42`) already established the working pattern for "create N sandbox SKUs now, fill the pricebook, production catalog re-created at flip" — the renewal SKU family will follow the identical playbook.

**Checkout** — `apps/site/lib/paddle-checkout.ts`:

- `openCartCheckout()` (`:67-85`) opens **one** Paddle.js overlay for N cart lines (`items: [{priceId, quantity}]`), stamping **`customData: { account_id: accountId }` once for the whole checkout** (`:82`) — not per line. Cart items are typed `kind: "module" | "edition" | "bundle"` (`apps/site/lib/cart.ts:18`); a renewal SKU would need a 4th cart-item kind or a separate non-cart single-item buy flow.

**Webhook verify** — `packages/billing/src/paddle-webhook.ts:43-66` — HMAC-SHA256 over `${ts}:${rawBody}`, 5s tolerance, timing-safe compare. Envelope schema `PaddleEventSchema` (`packages/billing/src/paddle-events.ts:39-43`) is **deliberately NOT `.strict()`** — a hard-won 2026-07-04 live-verification lesson (`paddle-events.ts:25-34`): a strict envelope 400'd every real Paddle delivery (extra documented fields), which on the money path means paid purchases never fulfill. Confirmed by the memory ledger (`remediation-closeout-live-proofs.md`).

**Event mapping** — `parsePaddleEvent()` (`packages/billing/src/paddle-events.ts:254-331`): `transaction.completed` with no `subscription_id` → `purchase.completed` carrying `lineItems[]` (each `{priceId, quantity, itemId (txnitm_…), chargedAmount}`, `:117-186`), `paymentId` = the transaction id, `accountId` from `custom_data.account_id` (`:58-63`, transaction-scoped, not per-line — Paddle's documented model, confirmed via `developer.paddle.com/build/transactions/custom-data`: custom_data attaches to the checkout/transaction/subscription/customer entity, never to an individual line item).

**Fulfillment** — `services/license/src/apply-billing-event.ts`, case `"purchase.completed"` (`:107-152`): loops `ev.lineItems`, `resolvePurchase(line.priceId)` fail-closed per line (`:128`), for each line: grants `line.quantity * purchase.credits` credits keyed `(paymentId, lineItemId)` (`:131-141`) and calls `grantEntitlements()` for `purchase.entitlements` keyed `(paymentId, lineItemId)` (`:142-148`).

**Grant store** — `services/license/src/entitlement-store.ts`: one row per `(account, entitlement, source, line_item)` in `entitlement_grant` (`:29-57`, widened by ADR-0218 `:113-118`). **Relevant column that already exists: `granted_at timestamptz NOT NULL DEFAULT now()`** (`:39`) — this is the natural anchor a 12-month window would measure from. **No `updates_expires_at` column exists.** Idempotency is `(account_id, entitlement_id, source_kind, COALESCE(subscription_id,purchase_id), COALESCE(line_item_id,''))` unique (`:53-54`) — a renewal purchase (new `purchase_id`) would NOT collapse into the original grant row; it would be a wholly separate insert under the current `grantEntitlements()` path if routed there unchanged.

**License issuance** is decoupled and lazy (`services/license/src/app.ts:1-9`, POST `/issue`) — keyed `(account_id, major)` (`license-grant-store.ts:43-44`), not triggered by the webhook at all. It reads current entitlements via `resolveAccountEntitlements()` (`resolve-entitlements.ts:25-32`) at issue-time. **This means the update-window enforcement point is downstream of both webhook fulfillment and license issuance** — it lives in the registry Worker's offline gate and/or `/issue`'s read path (ADR-0244 §"Consequences" already names this as future work), not in `apply-billing-event.ts` itself. This research's job is only the fulfillment-write side.

## 2. Renewal-SKU sandbox shapes

All three shapes are **mechanically identical at the fulfillment layer** — Paddle price ids are already the atomic key `resolvePurchase()` dispatches on, so "how many Paddle products" is purely a dashboard-organization question, not a fulfillment-logic fork. The real fork is **how fulfillment learns which entitlement/grant a renewal extends**.

| #     | Shape                                                                                                                                      | Paddle-side                                            | Fulfillment-matching mechanism                                                                                                                                                                                                                                                                  |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A** | Per-SKU renewal **product** family (mirrors today's 1 product = 1 SKU pattern; ~15 new sandbox products, one per renewable edition/module) | 15 new products × 1 price each                         | New `RENEWAL_BOOK: providerPriceId -> {renewsEntitlement: string}` — price id alone tells fulfillment which entitlement to extend. Zero new `custom_data`.                                                                                                                                      |
| **B** | **One** "Updates Renewal" product with **per-SKU prices** (1 product, 15 prices)                                                           | 1 product, 15 prices                                   | Identical to A at the code layer — still one unique price id per target entitlement. Only difference: Paddle dashboard shows renewals grouped under one product page instead of 15.                                                                                                             |
| **C** | **Additional price on the original product** (e.g. the Compliance product gains a 2nd price "12mo renewal" beside its "one-time" price)    | 0 new products, 1 new price per existing product (~15) | Same as A/B — each price still has its own unique `pri_…` id, so `resolvePurchase`-style dispatch is unchanged. Marginally simpler Paddle catalog (fewer product rows), but couples renewal pricing to the same product page as the original purchase (harder to retire/reprice independently). |

None of A/B/C need per-line `custom_data` to identify the **entitlement** — the price id already encodes it, exactly like every existing PURCHASE_BOOK row. The genuinely open question all three share: **when an account holds a purchase from an edition it already owns, or (rarer) the SAME entitlement from two separate one-time purchases, which specific `entitlement_grant` row's window does a renewal extend?** Paddle's `custom_data` is transaction-wide (not per-item — confirmed above), so it can carry `account_id` (already does) but not a target purchase/grant id if the renewal is cart-mixed with unrelated lines in the same checkout. Two ways to resolve this, **stated as an assumption for the parallel window-check research to confirm/override**:

- **Assumption (recommended default): track the window per `(account_id, entitlement_id)`, not per individual grant row.** A renewal extends every ACTIVE grant row for that pair uniformly (there is normally exactly one; if two exist — e.g. a duplicate purchase — extending both is safe, never under-grants). This sidesteps the "which specific purchase" ambiguity entirely and needs no new `custom_data`.
- **Rejected for v1:** per-grant-row windows disambiguated via an explicit `renew_grant_id` in `custom_data` — would force renewal checkouts to stay single-item-only (since custom_data is transaction-wide) and adds a buyer-dashboard "pick which purchase you're renewing" step for a case (duplicate purchase of the same SKU) that's rare enough not to warrant it now.

## 3. What the fulfillment handler must write for a renewal

Given assumption above, `apply-billing-event.ts`'s `purchase.completed` case needs a **new branch per line**, not a new event type (still the same `transaction.completed` → `purchase.completed` mapping unchanged, `paddle-events.ts:261-283`):

1. **Lookup**: a new `RENEWAL_BOOK` (parallel to `PURCHASE_BOOK`, versioned/append-only per ADR-0006) resolving `priceId -> { renewsEntitlement: string }`, fail-closed like `resolvePurchase`.
2. **Per line, branch on which book the priceId resolves against** (renewal book checked before/instead of the purchase book — a price id must live in exactly one, enforced by a test): if it's a renewal SKU, do **not** call `grantEntitlements` (that would mint a spurious new grant row per the current uniqueness index, since a fresh `purchase_id` never collapses with the original). Instead call a new `extendUpdatesWindow(tx, {accountId, entitlementId, months: 12, sourceEventId: paymentId})` that:
   - `UPDATE entitlement_grant SET updates_expires_at = GREATEST(now(), COALESCE(updates_expires_at, granted_at)) + interval '12 months' WHERE account_id=$1 AND entitlement_id=$2 AND status='active'` (a new nullable `updates_expires_at timestamptz` column, additive migration alongside `entitlement_grant`, same append-only-schema discipline as the `line_item_id` migration at `entitlement-store.ts:113-118`).
   - Fail-closed on **zero rows updated** (buyer renewing an entitlement they don't actively hold — no active grant to extend) — throw `ConfigError`, mirroring every other fail-closed grant path in this file (ADR-0089 §6 posture, `:82-87`, `:111-113`). Never silently create a fresh grant as a fallback — that would be an unpurchased-edition-shaped bug, not a renewal.
   - Renewal SKUs carry `credits: 0` always (no credit pack) — no credit-ledger write needed on this path.
3. **Idempotency**: already covered by the existing OUTER `processEvent` claim in `webhook.ts:57-77` keyed on `event.sourceEventId` (the whole transaction) — a webhook redelivery of the same renewal transaction is a no-op before `applyBillingEvent` even runs a second time, so no new idempotency key is needed inside `extendUpdatesWindow` itself.
4. **Refund symmetry** (not scoped to build now, but a gap to flag): `refund.completed` currently only knows how to revoke entitlement grants and claw credits (`apply-billing-event.ts:161-276`) — it has no notion of "un-extend a window." A refunded renewal would need its own branch (roll `updates_expires_at` back by 12 months, or simplest: floor it at whatever it was before, tracked via a small history/audit column) — out of scope for this research pass, flag for the execution spec.

## 4. Recommendation

**Shape B (one "Updates Renewal" Paddle product, per-SKU prices) — confidence: medium-high.**

Evidence: fulfillment-layer code is identical across A/B/C (price-id keyed dispatch, same as every existing book), so the deciding factor is Paddle-catalog hygiene and reprice ergonomics — and B keeps the _n_ renewal price points in one dashboard product/page (easier to audit "are all 15 renewal prices at ~40% of current list" at a glance, matches how ADR-0227 already treats per-module SKUs as a flat sandbox list to fill) while still letting each SKU's renewal reprice independently of A's 15-separate-products sprawl or C's coupling to the original product's page. It also cleanly signals in the Paddle dashboard "this whole product is the renewal program," which matters once the ~40%-of-list price needs to be bulk-adjusted after a base-edition reprice (as already happened once, ADR-0227).

Second-order recommendation (the part actually load-bearing for correctness, not just catalog taste): **track the window per `(account_id, entitlement_id)` via a new `updates_expires_at` column on `entitlement_grant`, extended by price-id → entitlement lookup, fail-closed if no active grant exists to extend** — this needs zero new `custom_data` plumbing and reuses every idempotency/fail-closed mechanism already in `apply-billing-event.ts`. Flag explicitly for the parallel window-check research to confirm this is the model it expects to read against at the registry-Worker/`\issue` gate (ADR-0244's named-but-unbuilt consequence).

## Top-line answer: does caisson get cited today?

**No — 0/9 cross-vendor probes and 0 organic-SERP hits mention Caisson**, and Exa's own index has **zero pages indexed for `caisson.sh`** (domain-restricted search returned an empty result set). This is not "indexed but skipped" — it is **not indexed at all**, and the root cause is structural, not a content or markup gap: **the entire production site sits behind a Cloudflare Access login wall**, confirmed independently by two different fetchers (`crawl4ai` and Exa's `web_fetch_exa`) hitting the identical "Log in to Caisson site (pre-launch gate)" page for `/`, `/robots.txt`, and `/llms.txt` alike. Every crawler — Googlebot, GPTBot, ClaudeBot, PerplexityBot, CCBot, Exa's own indexer — sees that same login form, not the site.

This is already known and tracked: `docs/gtm/aeo-crawlability-audit.md` (2026-07-07, two days before this audit) flagged it as the sole blocking item after certifying 15/15 code-level checks PASS, and `docs/state/decisions-and-forks.md` fork **A2** locks the gate's disposition ("keep gated until real checkout works + Compliance is buyable"), with a full mechanical runbook already written (`docs/state/launch-runbook.md` §4). **This audit's job is not to re-litigate A2** — it's to (1) confirm the gate is still up as of today with fresh cross-vendor evidence the code-only audit didn't have, (2) show exactly what's waiting behind it (verdict: excellent, nothing to fix), and (3) surface one scoping option A2 doesn't currently consider.

## Findings, ranked by citation-impact

### 1. [CRITICAL — blocks everything else] Cloudflare Access gate makes the entire site unindexable, unindexed today

**What's wrong:** `caisson.sh`, `/robots.txt`, `/llms.txt`, `/sitemap.xml` all return the CF Access `onetimepin` login page to every unauthenticated fetch — including bots. `robots.txt` itself must be fetchable unauthenticated per the standard; right now it isn't. Confirmed 2026-07-09 via two independent tools (`crawl4ai` raw-mode, Exa `web_fetch_exa`) and corroborated by Exa's search index holding zero pages for the domain.

**Effort / owner:** N/A — not a markup fix. This is `infra/terraform/access.tf`'s `site_gate` policy, an external-system side effect (Cloudflare) that is explicitly operator-gated (fork A2) and out of this audit's scope to touch or re-decide.

**What the runbook already has queued** (`docs/state/launch-runbook.md` §4.1): flip `cloudflare_zero_trust_access_policy.site_gate` from an email-domain allowlist to an `everyone`/bypass policy, tied to real-checkout go-live.

**New option this audit surfaces (not a decision, a scoping note for the ledger):** A2 currently bundles two distinct risks into one gate — "don't let crawlers/bots read marketing copy" and "don't let anyone hit real checkout before Paddle leaves sandbox." Those don't have to share a lock. A **path-scoped bypass** — an additional `cloudflare_zero_trust_access_policy` with `decision = "bypass"` applied only to GET on `/`, `/robots.txt`, `/llms.txt`, `/llms-full.txt`, `/sitemap.xml`, the `(marketing)` route group, and `/docs`, leaving `/dashboard`, `/api/*`, and the Paddle checkout surface fully gated — would let indexing/citation clocks start running (crawl-to-index lag is routinely weeks) without exposing checkout before Paddle goes live for real. Illustrative shape (same `site_gate` application, additional policy block, `infra/terraform/access.tf`):

```hcl
resource "cloudflare_zero_trust_access_policy" "site_gate_public_bypass" {
  account_id = var.cloudflare_account_id
  name       = "Caisson site - public AEO surface bypass"
  decision   = "bypass"
  include    = [{ everyone = {} }]
}
# then add to cloudflare_zero_trust_access_application.site_gate.policies with lower
# precedence than site_gate, scoped via a path include/exclude on the destinations —
# Cloudflare Access applications are host-scoped, not path-scoped, by default; a
# path-level split may require splitting site_gate into two applications (apex
# marketing+docs vs. /dashboard+/api) rather than one bypass policy on the existing
# host-level app. Flag for whoever executes this: verify path-scoping is achievable
# before committing to this shape — it may need an app split instead.
```

This is presented for `docs/state/decisions-and-forks.md` triage, not executed here — audit-only, and a Cloudflare topology change is an external-system side effect belonging to the main thread + operator sign-off regardless.

### 2. [S, once the gate above is resolved] Docs pages ship no canonical URL / OG / Twitter card

**What's wrong:** Every marketing page's `generateMetadata` runs through `buildMetadata()` (`lib/metadata.ts`) — self-referencing `canonical`, OpenGraph, Twitter `summary_large_image`. The docs route does not: `apps/site/app/docs/[[...slug]]/page.tsx` `generateMetadata` returns a bare `{ title, description }` with no `alternates.canonical`, no OG, no Twitter. This is exactly the "docs page citability" gap the brief asked about — an LLM or search engine that pulls a docs page by URL has no canonical signal telling it that's the authoritative location, and no OG card if the URL gets shared/previewed.

**The concrete fix** (file: `apps/site/app/docs/[[...slug]]/page.tsx`):

```ts
import { buildMetadata } from "@/lib/metadata";
// ...
export async function generateMetadata(props: Params): Promise<Metadata> {
  const params = await props.params;
  const page = source.getPage(params.slug);
  if (!page) notFound();
  return buildMetadata({
    title: page.data.title,
    description: page.data.description,
    path: page.url, // fumadocs' page.url is already the route path, e.g. /docs/local-first/local-privacy
    type: "article",
  });
}
```

`page.url` (confirmed in `lib/source.ts`) is already the exact path `buildMetadata` wants — this is a same-shape mechanical swap, not new plumbing.

**Effort:** S (one file, ~6-line diff, no new dependency).

**Headings/anchors:** not flagged — fumadocs' MDX pipeline auto-generates heading `id`s via its standard remark/rehype chain, so stable in-page anchors already exist for every doc heading; verified by pattern (not independently re-derived here), consistent with the framework default. No action needed unless a future spot-check finds otherwise.

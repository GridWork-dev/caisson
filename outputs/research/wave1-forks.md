# Wave-1 — surfaced forks (research fanout output)

Generated by the `wave1-fork-research` workflow (21 agents, 5 surfaces, **117 forks** + 13 cross-cutting). **Surfaces forks; decides nothing.** Every fork waits on an operator lock per the never-auto-decide rule.

**Legend:** 🔴 = operator-gated (genuine product/security/licensing/commerce judgment) · ⚪ = architecture w/ an ADR-backed recommendation (batch-approve per surface). Confidence is the research agent's.

## P2-compliance — 23 forks

> P2 (the Compliance hero) is mostly a WIRING + one net-new-generator surface, not a crypto rebuild: the load-bearing primitives are already shipped green in Wave-0 — `kernel/src/audit-chain.ts` (full SHA-256 chain + `anchorChain`/`verifyChain(entries,anchor)` tip-store), `kernel/src/versioning.ts` (pure append-only supersede graph, derived-current, fork-throws), and the entire `field-crypto/*` package (per-tenant HKDF, `KmsKeyProvider` envelope, self-describing envelope, fail-closed `withFieldCryptoContext`). The dominant seed is operator-owned Wardfile (harvestable patterns: WORM `ArtifactStore`, missing-GRANT immutability, config-as-code state modules, the golden harness, flag-never-guess) — the ONE thing Wardfile does NOT contain is a generic control-evidence-pack generator, which is P2's highest net-new build. The forks cluster into five data-layer decisions that gate the most code (where the stateful layers live; chain+anchor persistence; version schema; WORM store + retention mode; the withTenant×field-crypto composition owner), the field-crypto P2 wiring (DB-backed key stores, the sync/async KMS bridge), and the evidence engine (control registry, evidence format, determinism, flag-gate). FIVE forks are operator-gated and must NOT be auto-decided: row-level AAD (B4, already on the board), the entangled key-granularity↔crypto-shred GDPR-Art.17 decision (new), the control-mapping SOURCE (SCF is CC-BY-ND and collides head-on with fully-commercial ADR-0023 — a flag-never-guess licensing trap), the evidence-pack signing key/scheme (no scheme decided; needs an ADR amending ADR-0006), and whether evidence generation is credit-metered (commerce, ties to open Pricing). ADR-0006/0013 require golden-file regression BEFORE any evidence logic, so the format+determinism+flag forks gate the golden fixtures that gate the generator.

#### ⚪ P2-1 — Package decomposition & where the stateful DB layer lives (kernel is pure-function only) _(high)_

**Q:** The append-only-version table, the audit-chain store, and the key-version/wrapped-DEK tables are all STATEFUL, but `kernel` is pure-function-only and `field-crypto` deps are kernel-only. Which package owns each stateful store, and what is the down-only dep graph?

- **(a) field-crypto + audit-worm stay standalone paid PRIMITIVES owning their own stores: chain/version DB persistence in audit-worm, key/DEK tables in field-crypto; `compliance` is the EDITION that composes them. Graph: compliance → {audit-worm, field-crypto, tenancy-rls, credits?, kernel}** — Keeps à-la-carte commerce (each primitive independently sellable) and kernel pure; costs a slightly wider but still down-only dep graph and per-package migration ownership (see P2-22)
- **(b) Fold all DB persistence into the `compliance` edition** — Simplest single home, but kills à-la-carte sale of audit-worm/field-crypto as standalone primitives (ADR-0012) and bloats the edition
- **(c) A new `versioning`/`audit-chain` DB package separate from kernel** — Cleanest separation of pure-algorithm vs stateful-store, but adds a package + manifest + publish surface for a thin layer

**Rec:** (a) — primitives own their stores, edition composes. It's the only model that preserves à-la-carte commerce + a pure kernel while staying down-only (ADR-0003/0022).
**Gates:** Every manifest (P2-21), the dependency-cruiser graph, which package owns the version + chain + key schemas, and migration ownership (P2-22). This is the architectural keystone — most other forks assume its answer.
**Evidence:** field-crypto/manifest.ts:13 (dependencies:["@caisson/kernel"] only); versioning.ts:1-4 + audit-chain.ts (pure, no DB); ADR-0003/ADR-0022 (composable, down-only, never depend up on an edition); spec 00 primitive vs edition split; scaffold state (audit-worm/compliance src/.gitkeep only)

#### ⚪ P2-2 — Audit-chain entry + trusted-anchor persistence + append serialization (highest-value unbuilt fork) _(high)_

**Q:** `audit-chain.ts:7-13,116-127` is explicit that internal consistency alone misses tail-truncation and wholesale-rewrite — catching them needs a trusted `(length,tipHash,genesisHash)` anchor held in WORM/append-only storage OUTSIDE the chain. Where do (a) the chain entries and (b) the anchor get persisted, and how are concurrent per-tenant appends serialized?

- **(a) Entries in an append-only Postgres table (immutability by missing UPDATE/DELETE GRANT, Wardfile pattern); the anchor minted by `anchorChain()` on every append and `put` into the WORM `ArtifactStore` under a length-keyed object key; `verifyChain(entries, anchor)` reads both. Serialize appends via a per-tenant `pg_advisory_xact_lock` or a unique `(account_id, seq)` index + 23505→ConflictError retry** — Satisfies 'anchor outside the chain, in WORM' exactly; the length-keyed WORM key is write-once collision-proof; modest concurrency machinery
- **(b) Entire chain serialized into WORM objects, anchor in DB** — Inverts where immutability lives; loses the queryable SQL chain spine and the cheap DB-grant immutability
- **(c) (a) PLUS pin the anchor to an external timestamping authority (RFC-3161) or a Merkle/Rekor-style transparency log for public, split-view-resistant verifiability** — Real operational weight; overkill for a single-tenant evidence chain in v1 but the right shape if a PUBLIC verifiable ledger ever becomes a premium feature (P7 round-out)

**Rec:** (a) as the v1 floor (entries in PG, anchor minted per-append into WORM, advisory-lock serialization); transparency-log/RFC-3161 = a documented premium upsell, not the base.
**Gates:** The chain DB schema + migration, the anchor write path, the verifyChain wiring, the chain PAYLOAD shape (likely {account_id, version_id, checksum, supersedes_id, locked_at} via audit-chain.ts:66 canonicalize), and the append serialization point. Depends on P2-1 (which package) + P2-4 (the WORM store the anchor lands in).
**Evidence:** audit-chain.ts:7-13,116-142 (anchor outside chain; genesisHash optional :126); Wardfile db/schema/report-version.ts (immutability-by-missing-grant); SDK brief §2 (Rekor v2/Trillian/RFC9162 as the premium tier; QLDB rejected); ADR-0006:10-13

#### ⚪ P2-3 — Append-only locked-version DB schema + immutability mechanism _(high)_

**Q:** `kernel/versioning.ts` is pure functions over `VersionRecord[]`; P2 needs the persisted table. How is row immutability enforced, and is 'current' derived or stored?

- **(a) Wardfile pattern verbatim-in-spirit: append-only table, immutability by REVOKE UPDATE/DELETE from the `app` role (not a trigger); supersedes_id chain validated by kernel/versioning.ts on read; 'current' DERIVED via a no-successor SQL predicate; a `.strictObject` Zod JSONB `provenance` column parsed BEFORE the INSERT** — Cheapest immutability that composes with withTenant's app role; current can never drift; battle-tested in Wardfile
- **(b) (a) PLUS a defense-in-depth belt: a BEFORE UPDATE/DELETE trigger that RAISEs + a per-org pg_advisory_xact_lock** — Belt-and-braces against a SQL-injection/insider that somehow holds the grant; extra DB surface to maintain and test (the trigger-fires test composes with PGlite SET ROLE app)
- **(c) Artifacts only in WORM, PG holds refs** — Loses the queryable version spine and kernel/versioning.ts's structural validation

**Rec:** (a) as the spine, optionally + (b)'s REVOKE-plus-trigger belt. 'current = DERIVED' and 'linear-only (throw on fork)' are NOT open — they are locked by ADR-0006 + versioning.ts:1-8,45-53; confirm, don't re-decide.
**Gates:** The version schema + migration (grant-revoke + buildTenantPolicySql RLS policy), the supersede service, the version-query layer. Pairs with P2-2 (chain commits to the version row's checksum).
**Evidence:** versioning.ts:1-8 (derived current, throws-not-guesses), :45-53 (fork = throw); ADR-0006:8; Wardfile report-version.ts (missing-grant immutability, provenance-Zod-before-INSERT); ADR-0014 (RLS-in-migration); SDK brief §3 (PG REVOKE+trigger+advisory-lock 2026 consensus; PG19 still has NO system-versioning, so build-it-yourself is correct, not a gap)

#### ⚪ P2-4 — WORM ArtifactStore — port shape, real-SDK-vs-seam, backend provider, retention floor & per-tenant isolation _(high)_

**Q:** ADR-0006 names 'local + S3 Object-Lock backends'. Ship a real `@aws-sdk/client-s3` store now, or an un-wired seam-tested stub like `kms.ts`/ADR-0047? Which provider(s)? What retention floor and tenant-isolation scheme?

- **(a) Real `S3ArtifactStore` over @aws-sdk/client-s3 wired in Wave-1, e2e against minio** — Closest to production truth; pulls a cloud SDK + live integration into CI, against the Wave-0 'cloud call behind the port, no live CI call' ethos
- **(b) `ArtifactStore` port + a real `LocalArtifactStore` (dev/test backend) + an `S3ArtifactStore` unit-tested against an injected `S3Sendable = Pick<S3Client,'send'>` stub, NOT required in CI — mirrors kms.ts/ADR-0047. Write-once via S3 conditional `IfNoneMatch:'*'` (412→ArtifactExistsError) + ObjectLockMode/RetainUntilDate. Retention: calendar-correct `retainUntilFrom`, default 6–7yr HIPAA/SEC-safe floor, per-`put` override so DB `retain_until` == S3 date provably. Isolation: key prefix `{account_id}/…` + assertSafeKey + optional per-tenant SSE-KMS** — Matches every Wave-0 cloud-seam precedent; buyer wires the real SDK at deploy; the only un-exercised path in CI is the live S3 transport
- **(c) S3-compatible via a minimal signed `fetch` (no SDK dep)** — Avoids the SDK dependency, but you re-implement transport/retry/timeout the SDK gives for free

**Rec:** (b) — port + real Local + seam-tested S3 (injected S3Sendable, off the CI critical path), 6yr default retention floor, account_id-prefix isolation. It is the exact Wave-0 ethos (kms.ts:7-10,157-164; ADR-0047). Provider menu to surface: S3 (the only Cohasset/17a-4-assessed reference) / MinIO (self-host, same Object-Lock API) / R2 (already in the hosting stack — verify Compliance-mode parity before relying on it for 17a-4) / B2/Wasabi.
**Gates:** audit-worm/src/store.{ts,local.ts,s3.ts}, the ArtifactStore port shape, the retain-until helper, the key/SSE scheme. It is also the anchor home for P2-2.
**Evidence:** ADR-0006:10-13 (local + S3 Object-Lock, retention on row AND object, byte-stable checksums); kms.ts:7-10,157-164 (seam-real/cloud-behind-port precedent); ADR-0047 (un-deployed unit-tested seam); Wardfile core/artifact/{store.ts,store.s3.ts,store.local.ts}; SDK brief §1 (Cohasset 2025, MinIO/R2/B2 parity caveats)

#### 🔴 P2-5 — Object-Lock retention MODE — GOVERNANCE vs COMPLIANCE (the single most load-bearing compliance config) _(high)_

**Q:** COMPLIANCE mode = nobody (not even AWS root) can delete/overwrite before retain-until (the regulated SEC 17a-4 path); GOVERNANCE = bypassable by anyone holding s3:BypassGovernanceRetention + the bypass header. COMPLIANCE is irreversible and bricks a misconfigured dev bucket for years. What is the default?

- **(a) GOVERNANCE default; COMPLIANCE only at the paid SOC2/compliance tier; NEVER COMPLIANCE in local/test (the LocalArtifactStore ignores retention anyway)** — Safe for dev, court-admissible when the buyer opts into the tier; a GOVERNANCE-default prod bucket is technically bypassable until escalated
- **(b) COMPLIANCE always (strictest)** — Truly immutable everywhere, but bricks dev/test buckets and is unrecoverable from a bad retain-until
- **(c) Per-evidence-class mode (SSN/PHI → COMPLIANCE, routine → GOVERNANCE)** — Finest control, most config surface + the most ways to misconfigure the irreversible mode

**Rec:** (a) — GOVERNANCE default, COMPLIANCE gated at the SOC2/compliance tier, never in local/test. Wardfile's proven escalation; the only safe default that still reaches the 17a-4 bar when paid.
**Gates:** The S3ArtifactStore `mode` option, the apps/compliance tier wiring, the docs danger-warning. Couples to P2-4 + P2-9 (crypto-shred is the only GDPR-Art.17 'out' once an object is COMPLIANCE-locked).
**Evidence:** SDK brief §1 (Compliance = the regulated path, Governance bypassable via s3:BypassGovernanceRetention; Cohasset 2025); Wardfile store.s3.ts (GOVERNANCE-now / COMPLIANCE-at-SOC2 escalation); ADR-0006 SOC2-tier escalation language

#### ⚪ P2-8 — KMS async pre-resolve into the synchronous column hot-path _(medium)_

**Q:** `column.ts:6-7`: the Drizzle toDriver/fromDriver are SYNCHRONOUS; a KMS (async) provider must 'pre-resolve + cache keys into the context'. The mechanism is undecided.

- **(a) A per-request warm step resolving the key versions a transaction will touch (current for writes; envelope-declared versions for reads) into a sync-resolvable FieldCryptoContext.deriveKey closure** — Precise, transient DEKs; needs the caller to know which versions a txn touches up front (reads can pre-scan envelopes)
- **(b) A process-wide LRU keyed (tenant, version) with short TTL to amortize KMS Decrypt calls** — Amortizes KMS round-trips; a plaintext DEK now lives in an in-process cache (bounded TTL; never logged/persisted, kms.ts:9-10)
- **(c) Both — a warm step backed by a short-TTL LRU** — Best latency + correctness; most moving parts

**Rec:** (c) — a warm step that builds a sync key map, backed by a short-TTL in-process LRU; the plaintext DEK stays transient. Matches Wardfile's 'unwrap once at boot/per-request, never per row' discipline.
**Gates:** A KMS-backed sync-context adapter in field-crypto. Only fires if a buyer selects the KmsKeyProvider tier.
**Evidence:** column.ts:6-7 (sync codecs, KMS pre-resolve = P2 wiring not the sync hot-path); kms.ts:9-10 (DEK transient, never logged/persisted); Wardfile db/types/kms.ts (boot-time unwrap-once-cache pattern)

#### 🔴 P2-9 — OPERATOR-GATED (security) — field-crypto key granularity ↔ crypto-shred (GDPR Art.17 erasure) _(medium)_

**Q:** ADR-0043 base keys are HKDF-DERIVED (deterministic, ZERO stored key) — so there is NOTHING to delete to crypto-shred a single tenant/subject; rotating the master key or salt blasts everyone. Crypto-shred (destroy a STORED per-subject/tenant DEK to render WORM-immutable ciphertext permanently unreadable) is the EDPB-endorsed way to reconcile GDPR Art.17 with immutable retention — a direct selling point for the hero, but it forces a key-storage fork ADR-0043 deliberately avoided. Entangled with P2-10.

- **(a) Derived per-tenant keys only (current ADR-0043 default)** — Zero infra, no key-storage surface; NO crypto-shred and tenant is the finest erasure unit — sacrifices Art.17-by-key-destruction
- **(b) Stored per-tenant (or per-subject) DEK via the KmsKeyProvider port → `kms schedule-key-deletion` gives mechanical, sub-retention-window erasure + an `erasure.crypto-shred` audit event** — Unlocks regulated-buyer Art.17 SLAs at the key-storage/backup/rotation cost ADR-0043 avoided (ADR-0043:63-65 explicitly rejected stored keys at the BASE tier; per-SUBJECT keys are 'months of work, only if buyers ask')
- **(c) Hybrid — derived default, stored-DEK opt-in for regulated buyers needing Art.17** — Best of both, but two key paths to test and document; the crypto-shred path only at the upgrade tier

**Rec:** SURFACE ONLY (operator-gated, security-tagged → autonomy gate): the natural shape is (c) — keep derived as the base default (ADR-0043 stands), add stored-DEK crypto-shred behind the KMS port as the regulated-buyer upsell. Binding design note to carry regardless: if PII ever lands in a chained payload, the chain MUST commit to CIPHERTEXT (not plaintext) so the audit chain survives erasure.
**Gates:** The key-store design (P2-7 — whether WrappedKeyStore is load-bearing), the erasure event + audit row, whether P2-2's chained payloads commit to ciphertext, and the compliance edition's entire GDPR-erasure selling point. NOT a base-build blocker (base = derived, locked) but gates the regulated-buyer story.
**Evidence:** ADR-0043:14-31 (derived, zero stored key) + :63-65 (rejected stored per-tenant keys at base tier); kms.ts:63-103 (KmsKeyProvider stored-DEK path already built); SDK brief §4 (EDPB Guidelines 02/2025 + CNIL 2024 + ICO 2025 accept key-destruction as erasure; hash-over-ciphertext so the chain survives)

#### 🔴 P2-10 — OPERATOR-GATED (security) — row-level AAD (TM2, already on the board) _(medium)_

**Q:** `aad.ts:8-13`: the AAD binds tenant∥key_version∥column but NOT a row id, so a storage-write attacker can relocate/roll-back a ciphertext between two rows of the same tenant+column+version. Closing it needs a stable per-row id threaded into AAD via an explicit `encryptField(…, rowId)` call site — which CANNOT live in the transparent Drizzle customType (it never sees the PK). Entangled with P2-9.

- **(a) Leave column-scoped, document the residual risk** — Cheapest, keeps the transparent encryptedColumn ergonomics everywhere; no cross-row tamper-evidence (Wardfile itself relies on RLS+missing-grant+WORM, not row-AAD — so this is a new decision, not a regression)
- **(b) Add an explicit row-bound API `encryptField(ctx, columnContext, rowId, plaintext)` with AAD tenant∥kv∥column∥rowId for SEC/HIPAA fields** — Real cross-row defense; loses the transparent-column ergonomics at those call sites
- **(c) Hybrid — transparent column for low-sensitivity, explicit row-bound API for SEC/HIPAA-tagged columns; use crypto.randomUUID() PKs so rowId is known BEFORE the INSERT seals the cell (solves the chicken-and-egg)** — Targets the cost where it matters; needs a clear policy for which columns are row-bound + client-generated PKs on those tables

**Rec:** SURFACE ONLY (operator-gated; already open on decisions-and-forks.md:58): the natural shape is (c) hybrid + the randomUUID-PK caveat, but the board reserves this for the operator. Alternate to note: deterministic AEAD (AES-256-SIV) behind the existing AeadCipher seam can make the ciphertext itself a stable context-bound value, but it leaks plaintext-equality — keep as a documented alternate, never the default.
**Gates:** A row-bound encrypt API in field-crypto, which compliance columns adopt it, the golden fixtures asserting cross-row defense (or its documented absence).
**Evidence:** aad.ts:8-13 (column-scoped, no row id, named as the open Compliance-edition item); docs/state/decisions-and-forks.md:58 (operator-owned); ADR-0045 (AAD = tenant∥kv∥column); SDK brief §4 (Tink/AWS-ESDK 'bind ciphertext to context'; AES-SIV deterministic-AEAD alternate)

#### ⚪ P2-11 — Compliance control-registry authoring format & shape _(high)_

**Q:** The 'config-as-code module registry' for controls/frameworks — what authoring format, and OSCAL-native vs simple-data?

- **(a) Typed TS `defineControl({...})`/`defineFramework({...})` + Zod `.strict()` — mirrors the existing defineModule + Wardfile core/states/config.ts ('config change = commit = CI gate = reviewed diff; DB-resident config is the untested bypass'). **Rec:** (a) typed TS defineControl/defineFramework + Zod `.strict()` — it mirrors the proven defineModule + Wardfile state-module pattern, is golden-fixturable (which ADR-0006/0013 require before evidence logic), and matches the config-as-code thesis. Lula 2's defection FROM OSCAL is the cautionary data point against (c).
**Gates:** compliance/src/controls/* schema, the framework packs, the control golden harness. Frames where the EU-AI-Act empty slot (P2-18) lives.
**Evidence:** registry/schema/module-manifest.ts:123 (defineModule precedent); field-crypto/manifest.ts; Wardfile core/states/config.ts (Zod-.strictObject, 'config = reviewed diff', schema-version isCurrent invariant); ADR-0020 manifest ethos; SDK brief §8 (trestle vs Lula 2/Auditree; Lula 2 left OSCAL for YAML)

#### 🔴 P2-12 — OPERATOR-GATED (licensing, flag-never-guess) — control-mapping SOURCE + framework model (the SCF trap) _(medium)_

**Q:** SOC2-TSC and HIPAA overlap heavily, so one canonical control catalog + per-framework crosswalk is the model that scales to ADR-0040's framework set. But the SOURCE of the mappings is a binding licensing fork: the best-in-class crosswalk (Secure Controls Framework — 1,400+ controls, 200+ framework mappings, shipped as NIST OSCAL JSON) is CC-BY-ND 4.0 (NoDerivatives, explicitly extended to AI-generated derivatives) — which collides head-on with Caisson being fully-commercial (ADR-0023). An agent that just pulls SCF JSON into the product breaches the ND term.

- **(a) Ship SCF verbatim + attribution (no transformation)** — Free, but you're locked to SCF's exact IDs/structure and CANNOT fold it into Caisson's proprietary manifest shape
- **(b) Author Caisson's own thin SOC2/HIPAA control set, hand-mapped (the hero leads US frameworks)** — Fully owned, no third-party license, smaller surface; more authoring work, forgoes SCF's 200-framework breadth
- **(c) Buy an SCF commercial license (Tier-1 $25K/yr; Tier-2 $200K/yr + 20% of net sales; both restricted to 'GRC or similar platforms')** — Unlocks derivative mappings + breadth, but $25K–200K/yr and the 'GRC platform' restriction may not fit a sold CODEBASE LIBRARY
- **(d) Public-domain NIST OSCAL catalogs (800-53, FedRAMP) for NIST-anchored controls** — Sidesteps SCF entirely for NIST controls, but gives NO SOC2/HIPAA crosswalk — the exact thing SCF provides

**Rec:** SURFACE ONLY (operator-gated, licensing-binding — flag, never guess; do NOT auto-pull SCF). Framing: (b) own-authored thin SOC2/HIPAA is the cleanest fully-commercial path (ADR-0023, ADR-0040 leads US frameworks); the canonical-catalog + per-framework-crosswalk MODEL is the right scaling shape regardless of source.
**Gates:** The control catalog + crosswalk schema AND content, the framework packs, the EU-AI-Act slot content. A licensing breach risk if auto-decided.
**Evidence:** ADR-0023 (fully-commercial, every module LicenseRef-Caisson-Commercial except AGPL local-ai); ADR-0040:46-60 (SOC2/HIPAA lead, Vanta/Drata positioning, framework set); SDK brief §7 (SCF CC-BY-ND 4.0 + NoDerivatives-incl-AI + commercial-license tiers $25K/$200K, 'GRC platform' restriction); NIST IR 8477 STRM

## P3-ai-kit — 25 forks

> P3 (packages/ai-kit) is scaffold-only (src/.gitkeep); ADRs locked the credit/metering doctrine (0007/0024), provider-agnostic config shape (0011), composability/boundary gates (0003/0022), bun-test/golden harness (0013), and fully-commercial licensing (0023) — but none of the six P3 mechanisms has an implementation ADR. The architecture hinges on one load-bearing gap: ai-config is deliberately pure-config/no-network (config.ts:5), yet ADR-0011 binds "all inference routes through ai-config" and the boundary is enforced in code (boundaries.js PROVIDER_EXEMPT + .dependency-cruiser.cjs:42 force provider-SDK imports to live ONLY in ai-config|ai-kit). The surface wires five seams against a Postgres/multi-tenant/server-shaped Wave-0 substrate: a local inference compute seam + privacy gate, a local sqlite-vec + FTS5 vector/canonical store, offline Ed25519 license verify (rebuilt clean from PUBLIC tessera), a local canonical store + optional sync, and the AGPL contamination boundary — local-ai is the SOLE open flank (ADR-0023). Biggest blocking decisions in order: the AGPL package decomposition + build order, the AGPL dependency budget (needs a P4 ADR), the local inference runtime, the vector engine (sqlite-vec is brute-force NOT graph-ANN — the plan's "sqlite-vec ANN" is imprecise), and whether ANY sync ships in v1. **Rec:** B for the shared sqlite-vec/FTS utility (vendor AGPL copies — cheap, license-clean, manifest-compliant); license-verify is the exception and must be a commercial product-wide package decided with P4a-2. For `bunx create-caisson` / `npm create caisson` to work for buyers this needs resolution.

- **Compiled dist/cli.js + #!/usr/bin/env node shebang, node-runtime target** — Works for any buyer regardless of Bun; create-* packages are conventionally expected under plain node — but diverges from the Bun-first codebase
- **#!/usr/bin/env bun + ship TS** — Matches the codebase, but requires the buyer to have Bun installed
- **bun build --compile single binary** — Self-contained, but a heavier distribution per platform

**Rec:** Compiled node-target dist + shebang — buyers won't all have Bun and create-* packages run under plain node. Flip bin → ./dist/cli.js at publish and add the shebang.
**Gates:** The cli package build config + the bin/exports flip at publish.
**Evidence:** Verified packages/cli/package.json bin:create-caisson→./src/cli.ts; cli.ts has no shebang (line 1 = comment); build = tsc→dist; exports default ./dist/index.js

#### ⚪ P5-23 — How the published CLI obtains the registry index _(medium)_

**Q:** cli.ts:58-67 resolves the index from a CAISSON_REGISTRY_INDEX env path (dev-only) with the comment 'P5 bundles it with the published package.' A bundled snapshot is stale the moment a new module publishes; a fetch adds network.

- **Bundle a snapshot of index.json into the cli package at publish** — Zero network, but stale the moment a new module publishes (a fresh module is invisible to already-installed CLIs)
- **Fetch from the deployed Worker / a static URL at runtime** — Always fresh (ADR-0048's no-network rule is about GENERATION, not index fetch), but adds a network dependency and forces P5-25 (Worker deploy)
- **Bundled snapshot + optional refresh fetch** — Offline-safe AND not chronically stale; slightly more code

**Rec:** Bundle + refresh — the only option both offline-safe and not chronically stale. This directly forces P5-25 (whether the Worker/static URL must serve a fresh index).
**Gates:** cli.ts index resolution + the publish-time bundling step; couples to P5-25.
**Evidence:** cli.ts:58-67 ('P5 bundles it with the published package'); ADR-0048 no-network applies to generation not index fetch; ADR-0047 (static CI-built index is source of truth)

#### ⚪ P5-24 — Generated-repo install auth UX (the .npmrc token) — the P5/P6 boundary _(medium)_

**Q:** The generated .npmrc points at npm.pkg.github.com but carries no auth (generate.ts:94-96); installing paid @caisson/* modules requires the buyer's GitHub Packages PAT scoped to the org, and entitlement gating lives at P6. So 'the buyer can actually bun install the paid modules' is NOT fully closed by P5 alone.

- **Document a NODE_AUTH_TOKEN/~/.npmrc setup step in the generated README** — Closes P5 with no commerce infra, but the buyer does manual token setup
- **Generate a per-buyer scoped token at purchase** — Smooth UX, but pulls P6 commerce forward (out of P5)
- **Proxy installs through an entitlement-checking registry (the P5-25 Worker grown up)** — Best UX + enforces entitlement, but is the heaviest infra and is fundamentally P6

**Rec:** Documented token step for P5, design toward the entitlement-proxy at P6. Surface explicitly that paid-module install is not fully closed by P5 and depends on the P6 entitlement/license seam.
**Gates:** Generated README content + the P5↔P6 boundary.
**Evidence:** generate.ts:94-96 (.npmrc → npm.pkg.github.com, no auth); ADR-0047 (entitlement = P6); plan.md P6 §T6.2 (entitlement/registry-access on purchase)

#### ⚪ P5-25 — Deploy the registry read Worker at P5, or stay static-file? _(low)_

**Q:** ADR-0047 landed the Worker as a typed, unit-tested but UNDEPLOYED seam (worker/handler.ts, wrangler.toml), deferring real serving to 'P5/P6.' Whether it deploys is forced by P5-23: a fresh-index fetch needs the Worker (or an equivalent static URL) to serve it.

- **Deploy the Worker at P5 (Cloudflare account/route already exist; supply REGISTRY_INDEX via KV/R2 or bundled-at-deploy)** — The seam's intended growth path; hosts the P6 entitlement hook — but the most infra-heavy option
- **Serve index.json as a static file from the existing Cloudflare Pages site** — Simpler, no Worker runtime, but no place to grow the P6 entitlement hook (handler.ts // P6:)
- **Keep undeployed; CLI uses bundled snapshot only (P5-23 option a)** — No serving infra at all, but chronically stale CLIs

**Rec:** Lean defer — entitlement is the reason to deploy and that's P6; if P5-23 lands on bundle+refresh, a static index.json URL off the existing Pages site is the lightest fresh-index source. Deploy the Worker only if the operator wants the serving path live at P5. Confidence low/medium — it depends on P5-23.
**Gates:** Cloudflare deploy config + how REGISTRY_INDEX is injected + cache TTL; coupled to P5-23.
**Evidence:** ADR-0047 ('the Worker is a deferred seam, not a service … real edge serving + caching is P5/P6'); worker/handler.ts (typed, // P6: hook, cache-control max-age=60); CLAUDE.md hosting (Cloudflare Pages + caisson.sh)

#### ⚪ P5-26 — npm provenance / supply-chain attestation — accept the ledger substitute, or upgrade to GHEC attestations _(medium)_

**Q:** ADR-0021 names OIDC, but the 2026 landscape forecloses sigstore provenance for Caisson: npm trusted-publishing provenance is npmjs-only + public-repo-only, and GitHub artifact attestations on a PRIVATE repo require GitHub Enterprise Cloud. ADR-0021 already replaced 'trust an attestation string' with 'CI-only writer + git-tracked ledger + byte-identical rebuild.' Keep that, or pay for real provenance?

- **Accept no sigstore provenance; rely on the ledger + CI-only-writer + byte-identical rebuild as the chain-of-custody (the locked design)** — Cheapest, matches ADR-0021 exactly; the gateAttestation stays a recorded string not a signed statement
- **Upgrade to GHEC + add actions/attest-build-provenance@v4 on each published tarball** — Real SLSA-build-L2 cryptographic provenance for buyer trust, gated behind a GHEC plan (recurring cost)
- **Defer** — Revisit at P6 commerce when buyer-trust signals matter more

**Rec:** Accept the ledger/byte-identical substitute for P5 and record GHEC-attestation as an explicit 'declined/deferred' to keep the chain-of-custody story honest; revisit at P6. Low blast radius (a publish-job flag).
**Gates:** A publish-job flag only; the one place the locked design meets an external wall.
**Evidence:** ADR-0021 §Trust-model (ledger + CI-only-writer + byte-identical rebuild replaces the attestation string); ci.yml:63-76 (byte-identical check); SDK §1 (npm trusted-publishing = npmjs+public only; artifact attestations need GHEC for private repos)

## cross-cutting (completeness critic) — 13 forks

> Forks the per-surface agents each treated as local, but that are actually shared/unowned across surfaces. Most are 🔴 operator/architect decisions.

#### 🔴 X-1 — Ownership of new credit debit/grant event types (base-enum down-only collision) _(cross-cutting (credits ↔ P2/P3/P4a/P5))_

**Q:** When P2 evidence-pack generation, P4a hosted/'rented' inference, or any edition needs a NEW metered action, the debit type must be added to base credits' DEBIT_EVENT_TYPES (credits.ts:15 — today only codegen_debit/ai_feature_debit) and GRANT_EVENT_TYPES (credits.ts:11). An edition cannot depend 'up' (ADR-0003/0022), yet needs a base enum change. Do new event types live as a base-owned open enum, a registered string with per-edition validation, or does base ship a generic feature_debit editions tag — and who owns extending it?

**Why unowned:** credits is the shared money seam every edition meters through. An unmanaged enum either forces edition→base coupling (a down-only/ADR-0022 Gate-3 violation) or a free string (loses the typed-event guarantee). P2's 'is evidence-pack credit-metered', P3 metering, and P5 codegen all collide on this one enum, but no surface owns the extension model.

#### 🔴 X-2 — Global credit price-book + the recurring subscription-allotment issuer _(cross-cutting (commerce ↔ P3/P5/billing))_

**Q:** What is a credit worth, and how many credits does one generation (P5) or 1k tokens / one ai-feature call (P3) cost? ADR-0012 sells a monthly credit allotment and credits has a sub_allotment grant type (credits.ts:11), and billing emits subscription.created/updated/canceled (events.ts:21-30) — but NOTHING maps the recurring monthly cycle → grant(), and no component holds the codegen/ai-feature/USD→credit conversion table. Where does the price-book live, and who schedules the recurring allotment grant?

**Why unowned:** P3 surfaced 'integer-credit↔token/USD reconciliation' and P5 'codegen credit amount per generation' as if local, but both read ONE conversion table that also drives commerce; and the subscription MRR engine (ADR-0012's #1 retention lever) has emit-side billing events with no grant-side consumer. This is the carried Pricing board fork landing as concrete schema/runtime, unowned by any surface.

#### 🔴 X-3 — Migration assembly + single schema_version ledger across composed packages _(cross-cutting (P2/P4/P5 — DB/migrations))_

**Q:** ADR-0014 mandates ONE numbered, forward-only migrations/NNNN_*.sql sequence with a single schema_version checksum ledger, yet each composable package (credits, audit-worm, field-crypto, compliance, local stores) owns its own tables + RLS DDL (e.g. CREDIT_SCHEMA_SQL in credits/schema.ts). When the generator composes base+N editions into a buyer repo, who numbers and orders the merged migrations, and how does the one checksum ledger reconcile DDL contributed by independently-versioned packages?

**Why unowned:** P2 lists 'cross-package migration ownership + ordering' as an intra-compliance fork, but the real collision is at composition/generation time across editions: a per-package numbering scheme can't produce ADR-0014's single ordered sequence + one schema_version ledger without a merge authority. Unowned between P2, P4, and the P5 generator.

#### 🔴 X-4 — Entitlement expansion model: edition/bundle → member-module set _(cross-cutting (mcp-server/license/registry — P5/P6 boundary))_

**Q:** mcp-server entitlements are a flat string[] of slugs (server.ts:22) and the registry index has no bundle/edition→modules relation; manifests carry editions:[] membership (module-manifest.ts:63) but nothing resolves 'buyer owns edition compliance ⇒ entitled to {audit-worm, field-crypto, compliance}'. Who expands an edition or bundle purchase into the per-module entitlement set the MCP/CLI allowlist gate checks?

**Why unowned:** ADR-0012 sells whole editions, a discounted bundle, AND per-module à-la-carte — three grains that all collapse to one flat entitlement list at the gate. The expansion authority (license issuer? registry-derived membership graph? manifest editions[]?) is the join between commerce and the allowlist and no surface owns it. P5's 'entitlement vs allowlist timing' is about WHEN to enforce, not the expansion DATA MODEL.

#### 🔴 X-5 — Shared event-sink port + shared home for evidence/usage/eval schemas _(cross-cutting (observability — all editions + P6))_

**Q:** Is there a base EventSink/observability port (logs→OTel/Postgres) every edition emits operational telemetry through — spend, latency, eval scores, guardrail blocks, generation events — and do the evidence-pack (P2), usage-metering (P3), and eval-result (P3) SCHEMAS live in a shared base location so the P6 dashboard/docs/bot read one contract? Or does each edition log + define ad hoc? And is the compliance WORM audit-chain the same sink or strictly separate from operational telemetry?

**Why unowned:** The kernel ships an error model (errors.ts) but NO structured-event emission port; the only durable log today is the tamper-evident audit chain, which is not operational telemetry. The prompt's 'shared evidence/usage schemas' + 'shared observability' have no owner — three editions inventing their own event shapes blocks any cross-edition dashboard and re-litigates ADR-0019 redaction discipline per edition.

#### 🔴 X-6 — What ships INTO the buyer's generated repo vs stays Caisson-internal _(cross-cutting (P5 generator + every edition))_

**Q:** Which artifacts cross into the generated repo — the CI gate config (ADR-0016's 6 jobs), golden fixtures (ADR-0013), the standards-gate, migrations, the eval CI gate (P3), AGENTS.md — and which are Caisson-monorepo-only? Does the buyer's generated app carry its own CI/eval/golden harness, and under what license/posture?

**Why unowned:** Nearly every enforcement fork (CI jobs, golden-file regression, eval gate, lint gates) was authored for the Caisson MONOREPO, but the product IS a generator (Option C) emitting a buyer repo. The monorepo-vs-generated-artifact boundary silently changes the answer to many surface forks (P2 golden, P3 eval gate, P5 templates) and is assumed, never decided, by any surface.

#### 🔴 X-7 — Shared app-shell + multi-edition composed reference app + the mixed-license app _(cross-cutting (apps — ADR-0044 / P2-P4))_

**Q:** Six reference apps are scaffolded (apps/{base,compliance,ai-kit,local-ai,agent-dev,studio}). Is there a shared app-shell/apps/base substrate the edition apps extend (one auth/session/token wiring per ADR-0044), or is each a hand-wired Next app? Is there a COMBINED reference app for a buyer who owns compliance+ai-kit? And what SPDX license does a reference (or generated) app composing AGPL local-ai alongside commercial editions carry?

**Why unowned:** ADR-0044 locks Next.js but not whether apps share a shell or compose across editions; P4b only asks 'combined vs separate P4a/P4b apps'. The mixed-license question is sharp: ADR-0023 makes local-ai AGPL the SOLE open flank, and AGPL linked into one app/process with commercial editions is a real copyleft-propagation fork no surface owns.

#### 🔴 X-8 — Tenant isolation in the local/SQLite world (withTenant is Postgres-RLS-only) _(P4a-local-ai + P4b-agent-dev (tenancy))_

**Q:** The base tenancy invariant is fail-closed Postgres RLS via withTenant (ADR-0005), with 'encryption boundary == RLS boundary' (kickoff). local-ai and agent-dev stores are SQLite (bun:sqlite), which has no RLS. How is per-tenant isolation enforced there — one DB file per tenant, an app-level tenant_id filter, or is local-ai explicitly single-tenant — and how does that reconcile with the ADR-0005 boundary invariant the editions inherit?

**Why unowned:** Both local surfaces consume the base tenancy model conceptually but cannot use its mechanism; P4a's 'local store ORM' fork picks Drizzle-vs-raw-sqlite but skips the isolation SEMANTICS, and P4b 'memory schema + scope/tenancy model' assumes a model that doesn't exist on SQLite. Left implicit, the 'RLS == encryption boundary' invariant silently fails to hold in the privacy-first edition — a security regression.

#### 🔴 X-9 — Inference gateway × the ADR-0022 provider-SDK boundary (Gate 2) _(P3-ai-kit (enforcement))_

**Q:** ai-config today only RESOLVES provider config and makes no calls (config.ts — pure logic, no network). ADR-0022 Gate 2 forbids packages importing provider SDKs except behind the sanctioned seam. ai-kit's inference gateway must actually call providers — does it import the openai/anthropic SDKs (tripping Gate 2), get a documented carve-out, or force a NEW base InferenceClient port added to ai-config? Who owns that base-package change?

**Why unowned:** P3 lists 'provider-call abstraction backing the gateway' but not the lint-gate collision, nor that the call-side port must live in BASE ai-config (down-only), reopening a Wave-0 'locked' seam. The boundary lint (ADR-0022) will fail the build if this is left implicit — an enforcement decision, not just an architecture preference.

#### 🔴 X-10 — The eval CI gate as a 7th required job vs ADR-0016's locked 6 _(P3-ai-kit (enforcement/CI))_

**Q:** ADR-0016 binds exactly '6 required CI jobs (build·lint·unit·integration·standards-gate·golden-file)'. P3's eval-harness CI gate is a 7th required check. Does adding it amend ADR-0016, is it required-on-merge or advisory, and does it run only in the Caisson monorepo or also ship into the buyer's generated repo?

**Why unowned:** P3 surfaced 'CI gate policy + threshold/baseline storage' as an internal eval concern but missed that it collides with a numerically-locked ADR AND the generated-repo boundary. A required-status-check change is also governance (branch protection / the carried registry-prevention-gate operator action), not a code-only decision.

#### 🔴 X-11 — field-crypto row-AAD + per-tenant-key decisions inherited by non-Postgres reuse _(cross-cutting (carried board fork — P2 → P3/P4a))_

**Q:** The carried row-AAD board fork (column-scoped vs row-bound, decided at P2 per decisions-and-forks.md open-fork TM2) sets the AAD/key contract that P3 PII-redaction and P4a local at-rest encryption REUSE. Row binding needs a stable PK threaded through an explicit encryptField(…, rowId) call site the transparent Drizzle customType can't provide (column.ts) — and SQLite/local has no RLS/customType seam at all. Is row-AAD resolved once in P2 and inherited, or does the local/PII reuse get its own AAD + key-store resolution?

**Why unowned:** The board flags row-AAD for the Compliance session only, but field-crypto is explicitly reused by P4a ('field-crypto reuse vs device-key') and possibly P3 ('possible field-crypto reuse') — those reuses inherit a decision made for a Postgres column model that doesn't exist locally. An unowned cross-surface dependency on a security fork that the per-surface lists treat as local to each.

#### 🔴 X-12 — Per-edition extension of the buyer-facing MCP server _(cross-cutting (mcp-server — P2/P3 buyer-MCP extensibility))_

**Q:** The buyer MCP exposes a fixed tool set — list_modules/describe_module/generate (server.ts:134) behind a hard switch. Do editions EXTEND it with edition-specific buyer tools (compliance 'explain control X', ai-kit 'run eval', agent-dev kernel introspection), and if so who owns tool registration + per-tool entitlement gating + the MCP resources/prompts surface? Or is the buyer MCP frozen to generation only?

**Why unowned:** ADR-0008's buyer MCP is a headline differentiator ('agent-native delivery'), but it is currently generation-only and closed to extension. P5 owns the generate transport/auth; nobody owns whether editions may add tools — which determines if the MCP is a product surface or just a generator RPC.

#### 🔴 X-13 — Independent vs lockstep edition versioning + edition→member-version pinning _(P5-generator (packaging/versioning across editions))_

**Q:** Does each module version independently, or do an edition's member modules move in lockstep? Does an edition manifest PIN its member-module versions for a reproducible edition, or just name dependencies (module-manifest.ts dependencies:[] carries NO version; registry-index tracks per-module versions with no edition→member-version lock)? How is 'install Compliance edition @1.4.0' resolved to an exact member-module version set?

**Why unowned:** P5's changeset/backfill forks are about publish MECHANISM; this is the product semantics of what a versioned 'edition' MEANS when it's a composition of independently-published modules. Without an edition-level version lock, the Option-C reproducible-generate promise and the subscription 'framework updates' SKU (ADR-0012) have no deterministic version target. Unowned by any surface.

# 429/502 root-cause — 2026-07-09 (CAISSON-71)

**Disposition: harness false-positive, NOT a buyer-facing problem.** No production WAF/rate-limit
change is needed. The fix (if any) is a harness change in `apps/site/scripts/visual-harness.ts` —
**sibling-G's tree** (Kickoff-H does not edit `apps/site/**`); this doc is the handoff.

## The named endpoint

**`GET /api/auth/get-session`.** Every page render mounts `NavAccount` (always-visible in the site
nav — `apps/site/components/nav-account.tsx:26`), which calls `authClient.useSession()`
(better-auth's client hook). That hook fires a `GET /api/auth/get-session` request on mount, on
**every page**, unconditionally — there is no page in the harness's crawl set that skips it.

## Why it 429s

The Cloudflare edge WAF rate-limits `/api/auth/*` (`infra/terraform/waf.tf:54-77`, ADR-0219 CF-2):

- **Threshold:** `var.rate_limit_requests_per_period` = **60** requests
  (`infra/terraform/variables.tf:46`), **fixed 10-second counting window** (Free-tier
  constraint — not tunable without a Pro-plan upgrade), keyed on `["cf.colo.id", "ip.src"]`.
- This is the SAME rule that also covers `/query` (`services/docs`' embedding endpoint) — Cloudflare's
  Free plan allows exactly one `http_ratelimit` rule per zone, so both expensive paths share one
  threshold (`waf.tf`'s own header comment, "Zero-headroom note").

The site's own visual-regression harness (`apps/site/scripts/visual-harness.ts:591`) drives
screenshots through `asyncPool(4, jobs, ...)` — **4 concurrent Playwright workers**, each calling
`shootOne` (`:322`), which opens its own `browser.newContext()` (`:349`) and navigates a fresh
page. Every one of those page loads triggers `NavAccount` → `GET /api/auth/get-session`, and all 4
workers run from **one machine, one egress IP** (the runner/operator box). Four concurrent page
loads easily clear 60 requests inside a single fixed 10-second window once the harness is stepping
through a full surface sweep (legal/glossary/module/marketplace routes in quick succession) — the
WAF fires exactly as designed, against the harness's own concurrency, not against real buyer
traffic.

## The evidence

Two 429 clusters observed in the same run, each spanning ~9 seconds — both fall inside a single
fixed 10-second WAF counting window:

- **16:57:17–16:57:27 UTC**
- **16:57:53–16:58:02 UTC**

Both windows align with the WAF's fixed 10s bucket boundary, which is the signature of "one
counting window tripped," not a sustained or growing problem. A real low-traffic buyer session —
one browser tab, one page load, one `get-session` call — never approaches 60 requests/10s from a
single IP; this threshold is calibrated for a single visitor's browsing pace, not a headless
4-way crawler.

## Disposition

**Not a buyer problem.** No production WAF/rate-limit config change is warranted — loosening the
`/api/auth/*` threshold to accommodate a test harness would weaken the login-endpoint protection
this rule exists for (ADR-0219 CF-2's stated purpose: origin-$/abuse protection on
`/api/auth/*`, "currently zero rate limiting anywhere" before this rule shipped).

**The fix belongs to the harness, in `apps/site/scripts/visual-harness.ts` — sibling-G's tree.**
Two independent shapes (either is sufficient; G decides):

1. **Lower `asyncPool`'s concurrency** below whatever keeps the 4-worker `get-session` fan-out
   under 60 req/10s for the busiest sweep segment, or
2. **Stagger** worker starts (a small jittered delay per worker) so the 4 concurrent `NavAccount`
   mounts don't land in the same 10s WAF bucket.

Handoff: this doc + the two file:line pointers above (`visual-harness.ts:591` for the
concurrency, `nav-account.tsx:26` for why every route pays the `get-session` call) are everything
G needs to land either fix — no further H-side investigation required.

## Not the same issue: two isolated 502s

The same harness run also recorded two isolated 502s — one on `marketplace/plans`, one on
mobile-nav. These are **NOT** the `get-session` rate-limit signature (a 502 is an origin/gateway
failure, not an edge 429) and do not share the two clustered timestamps above. Read as **separate,
transient Railway cold-start blips** (a fresh container serving its first request before its
runtime is fully warm) rather than a reproducible bug — consistent with this repo's prior
cold-start-class incidents (`docs/deploy/STATE.md`'s 2026-07-01 entry: "the Next-standalone
`HOSTNAME=0.0.0.0` bind fix for a boot 502").

**Flagged, not fixed here:** correlating these two 502s against the Railway deploy logs for the
capture window (to confirm the cold-start read, or rule it out) is follow-up work, not resolved by
this root-cause pass — file a Linear ticket if a repeat is observed on a subsequent harness run;
a single occurrence on a cold path is not actionable on its own.

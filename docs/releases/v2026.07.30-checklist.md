## Attestations and caveats — read with the boxes above

Boxes are checked against what was actually done. Four carry qualifications that belong on the
record rather than buried in the audit:

- **Box 3 (CI green on the release SHA), and what the tag targets.** The tag targets `80748af3`,
  not the version-PR commit `ee467149`. One commit landed after the audit was written and rides
  this tag: `80748af3`, which stops `deploy-railway` from reading a dropped build-log stream as a
  failed deploy. It was not optional for this ride — the false RED had already half-deployed the
  fleet once (admin deployed, site skipped) and leg 4 would have hit it identically, _after_ legs
  1–3 published irreversibly. Reviewed as audit §9; readiness check 0 accepts any commit that is
  an ancestor of `origin/main`.

- **Box 5 (R4 audit).** Both lanes ran: `gw-security-auditor` (fable) on the money/licence/crypto
  seams and `gw-code-reviewer` (opus) on correctness and release integrity, independently and
  without sight of the main-thread pass. They returned **three blockers the main-thread pass
  missed**, all fixed pre-tag (§8 of the audit): `sot` red on `main` (would have stopped the train
  at leg 0), the leg-4 deploy-ordering break, and the kernel doc flip. Cross-verification also
  caught one **wrong** finding from the security lane — it held the legacy bearer branch was already
  removable, when the deploy it cited _precedes_ the change that needs it; acting on it would have
  caused the outage the other lane found.
- **Box 6 (live-hybrid leg).** Green: 13/13 with real keys. **But the leg does not discriminate** —
  re-run with an invalid key and a cleared embed cache it still passes 13/13 in 2.2s, because
  `HAVE_KEY` tests presence rather than validity and the goldens are satisfiable on the FTS floor.
  Even the real-keys run served 4 of 13 queries on that floor. Read this box as "FTS retrieval
  goldens pass", not as live-hybrid assurance. Detail: audit §5 D6.
- **Box 9 (no open P0/P1 on the install path).** True for the _install_ path. Separately, the
  `native-ext (macos)` check is red on every `main` push — the hosted runner cannot start
  ("recent account payments have failed or your spending limit needs to be increased"). It is not
  in `REQUIRED_CHECKS` and does not touch the buyer install path, but macOS native-extension
  coverage is dark. Operator decision, deferred 2026-07-30, tracked in `docs/state/outstanding-work.md`.

### One gap this ride exposed — CLOSED 2026-07-31

**The train had no registry-Worker leg, and a published version is not resolvable without one.**
Fixed the day after: `deploy-worker.yml` deploys the Worker from an ancestry-verified ref and proves
the live edge serves that ref's index before reporting green, and the train runs it as leg 1b (after
leg 1 uploads the bytes, before leg 4 puts the site live). The original finding is preserved below.

**A second instance of the same class was found while closing it:** `caisson-license` also bakes
`registry/index.json` into its image, and leg 4 deploys only admin and site — so license is still on
the pre-release `4810e38157c1` while repo/Worker/admin are on `dc5ee000aebf`. Tracked in
`docs/state/outstanding-work.md`; it needs one receipted redeploy.
Leg 1 uploads tarballs to R2, but the Worker inlines `registry/index.json` at build time, so the
edge kept serving `0.6.0` after a green train. Between leg 4 and the manual
`registry/worker/deploy.sh` the site advertised `@caisson/kernel/node` against a registry that
resolved `0.6.0`, where it does not exist. Closed by hand (Worker `d5e82c9b`); the class is filed
in `docs/state/outstanding-work.md`. Readiness check 4b does not cover it — it validates the repo's
index/tarball consistency, never what the live edge serves.

Also worth recording: **edge propagation is not instant.** For about a minute after
`wrangler deploy` the packument still served the previous `dist-tags.latest`. Probing immediately
after a deploy reads stale — wait a minute before concluding it failed.
